feat(lifecycle): implement Business and Outreach Identity lifecycle contracts

Both lifecycles were declared in the schema and unreachable from the application. What was missing was
the transition itself, the block that makes it mean something, and a guard against the destructive
alternative.

**Business lifecycle** (migration 0023, 0024)

- `archive_business` / `restore_business` — audited, admin-only RPCs. Archiving reports what it
  preserved, pauses active enrolments and invalidates unsent outreach; SENT messages are untouched.
  It is idempotent, so a retried request is not reported as a failure.
- `business_is_open()` — deliberately NOT folded into `has_business_access()`. That function decides
  *visibility*, and an archived business must stay readable so its history remains available.
  Conflating the two would make archiving indistinguishable from deletion.
- A `BEFORE INSERT` trigger on `leads`, `sequence_enrollments`, `message_instances` and
  `import_batches` refuses new work in an archived business. A trigger rather than an assertion in each
  writer, because the set of writers is large and open — repository, MCP tool, ingest pipeline, seed
  script — and a single trigger per table cannot be forgotten by the next caller.
- `archiveBusiness` / `restoreBusiness` / `deleteBusinessPermanently` in `repo/businesses.ts`, plus the
  server actions in `app/(app)/businesses/[id]/actions.ts`.
- `listBusinesses` now excludes archived businesses by default, which is what takes them out of the
  sidebar, the admin switcher, the Companion selector and `list_accessible_businesses`.
- Permanent deletion is refused when any protected history exists, with the counts, and again by a
  `BEFORE DELETE` trigger. `businesses` is the root of cascading foreign keys, so a delete destroys
  every lead, message version and event, reply, note and task it owned. The `allowed_hard_delete()`
  setting deliberately does not unlock this guard: purging a trashed lead and destroying a tenant's
  entire history are different questions.

**Outreach Identity lifecycle** (migration 0025)

- `unassignIdentity` / `archiveIdentity` / `deleteIdentitySafely` in `repo/identities.ts`, plus the
  server actions. Unassign deliberately does not write an `identity_transfers` row: that table names a
  recipient, and "nobody has this now" is not a transfer.
- Archiving sets `status = 'retired'`, revokes every live `browser_sessions` row in the same
  transaction, and is terminal — the database refuses a reactivation, because un-retiring would make
  the historical attribution of everything the identity sent ambiguous.
- **`identity_usable_by_actor` had a real defect**, and it was the reason "archive" would not have
  worked: `is_admin()` was tested *before* the identity was examined at all, so an admin bypassed its
  state entirely, and the owner branch checked `deleted_at` but never `status`. The active check is now
  stated once, before any branch.
- Deletion returns a typed rejection (`errorCode: 'identity_has_attribution'`) with the counts when
  history references the identity. This is the one gap that was silently destructive: every foreign key
  pointing at `outreach_identities` is `on delete set null`, so deleting an identity that had sent
  messages *succeeded* and blanked the sender on all of them. The message text survived with nobody
  attributed to it, and nothing reported the loss. A trigger now refuses it.
- Archived identities disappear from `listIdentityOptions`, `companionIdentities` and the assignment
  list, and stay visible on `/identities` marked retired — archiving is not hiding.

**Three further defects the new tests found**

1. `nexus.submit_candidate` wrote `ingest_requests.status = 'processing'` and then `'completed'`.
   Neither is in the check constraint (`received`, `processed`, `failed`, `duplicate`), and because the
   ledger row shares a transaction with the lead, the violation rolled the whole ingest back. **Every
   externally ingested candidate failed at the first write**, and the path had no test. Same defect the
   Companion capture route documents having already fixed for itself in `companion/add/route.ts`.
2. `ingest.ts` inserted `leads.source_type = 'api_ingest'`, which is not in `LEAD_SOURCE_TYPES` and not
   permitted by `leads_source_type_check`. Now `external_ingest`. (The string survives only as a filter
   bar *label*, which is where the literal was probably copied from.)
3. `requireScope` was called with `businessId ?? ''` for every tool, including
   `nexus.list_accessible_businesses` — the one tool that is not business-scoped, because its purpose is
   to discover which businesses a token reaches. It answered `-32003 "not scoped to that business"` for
   a token whose scopes were correct, so a client could never get past discovery.
